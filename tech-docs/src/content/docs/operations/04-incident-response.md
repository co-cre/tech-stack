---
title: 障害対応
description: インシデント対応の基本フロー
---

障害発生時に迅速かつ冷静に対応するための手順。

## 方針

- まず影響範囲を把握
- 復旧を最優先、原因究明は後
- 記録を残す

## 障害レベル

| レベル | 定義 | 対応 |
|--------|------|------|
| Critical | サービス全停止 | 即座に対応、全員招集 |
| High | 主要機能停止 | 担当者が即座に対応 |
| Medium | 一部機能に影響 | 営業時間内に対応 |
| Low | 軽微な問題 | 通常の優先度で対応 |

## 対応フロー

### 1. 専用チャンネル作成

障害を検知したら、まず専用チャンネルを作成。

```
#incident-2025-01-23-api-down
```

- 命名: `#incident-YYYY-MM-DD-概要`
- 関係者を招待
- 全てのやり取りをこのチャンネルで行う（後で追跡可能）

### 2. 影響範囲を記載

チャンネル作成後、すぐに影響範囲を投稿。

```
【障害発生】
- 発生時刻: 2025-01-23 14:30
- 影響範囲:
  - ユーザー: 全ユーザー / 一部ユーザー / 社内のみ
  - 機能: ○○機能が利用不可
  - データ: データ損失なし / あり
- 原因: 調査中
- 対応者: @xxx
```

影響範囲が不明な場合も「調査中」と明記。

### 3. ビデオ通話で接続

**Critical / High の場合はビデオ通話をつなぐ。**

- Google Meet / Slack Huddle などで常時接続
- 画面共有しながら調査・対応
- 口頭でのやり取りは後でチャンネルにも記録

メリット:
- リアルタイムで状況共有
- 判断が速い
- 孤独に対応しない

### 4. 調査

**確認コマンド**

```bash
# Workersのログ確認
wrangler tail --format json

# 最近のデプロイ確認
wrangler deployments list

# D1の状態確認
wrangler d1 info mydb
```

### 5. 復旧

**よくある復旧パターン**

| 原因 | 対応 |
|------|------|
| デプロイ起因 | ロールバック |
| 外部API障害 | フォールバック有効化 |
| DBの問題 | 接続プール確認、リトライ |
| トラフィック急増 | レート制限強化 |

**ロールバック**

```bash
# 前のバージョンに戻す
wrangler rollback
```

### 6. 復旧確認

```
復旧確認
├── ヘルスチェック: OK
├── 主要機能の動作確認
├── エラー率が正常値に戻った
└── Slackで復旧報告
```

**復旧報告**

```
【復旧完了】
- 復旧時刻: YYYY-MM-DD HH:MM
- 影響時間: XX分
- 原因: ○○
- 対応: ○○
- 詳細は後日ポストモーテムで共有
```

### 7. ポストモーテム

障害収束後、以下を記録：

```markdown
# インシデントレポート: YYYY-MM-DD

## サマリー
- 影響時間: XX分
- 影響範囲: ○○ユーザー
- 根本原因: ○○

## タイムライン
- HH:MM アラート発生
- HH:MM 調査開始
- HH:MM 原因特定
- HH:MM 復旧完了

## 根本原因
○○の処理で○○が発生

## 再発防止策
- [ ] ○○のテスト追加
- [ ] ○○の監視強化
- [ ] ○○のドキュメント更新
```

## 連絡先

```ts
// 障害時の連絡先（例）
const contacts = {
  primary: 'Slackチャンネル #incidents',
  escalation: '○○さん（Slack DM）',
}
```

## チェックリスト

### 障害発生時

- [ ] 専用チャンネル作成（`#incident-YYYY-MM-DD-概要`）
- [ ] 影響範囲を投稿
- [ ] Critical/Highならビデオ通話開始
- [ ] ログを確認
- [ ] 最近のデプロイを確認
- [ ] 外部サービスの状態を確認

### 復旧後

- [ ] 復旧報告をSlackに投稿
- [ ] エラー率が正常に戻ったことを確認
- [ ] ポストモーテムをスケジュール
